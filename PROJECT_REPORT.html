Power Profile

Building Energy Analysis Platform — Full Technical Report

Graduation Project  |  Full-Stack Web Application  |  Backend: Laravel 13 (PHP 8.3)  |  Frontend: React 18 + Vite  |  Database: SQLite  |  Report Date: May 2026

1. Project Overview

Power Profile is a full-stack web application designed to help engineers and architects model, analyse, and manage the electrical power consumption of buildings. It provides a structured hierarchy (Project → Building → Floor → Room) where electrical components are assigned at every level, and the system computes load profiles, peak demand, and optimal dispatch of power sources (solar, grid, generator).

Core Capabilities

  • Define multi-building projects with a four-level hierarchy
  • Attach electrical components (AC units, lighting, motors, etc.) at any level
  • Model power sources: utility grid lines, generator backup lines, solar panels
  • Calculate 24-hour load profiles based on component usage schedules
  • Simulate priority-based dispatch (Solar → Grid → Generator)
  • Backup and restore configurations (local file or server storage)
  • Collaborate with a team using role-based access control
  • Google OAuth authentication — no separate password management needed

3. Database Schema

The database uses SQLite with 15 tables. The design follows a strict hierarchy for buildings, a polymorphic pattern for shared power-source entities, and a separate component-type catalogue for reusable presets.

6. Business Logic Services

BackupExporter.php

Converts any entity into a fully nested JSON snapshot suitable for backup, restore, or duplication. Exports name, area, all components (with every field), utility lines, generator lines, sockets, and recursively exports all children (buildings → floors → rooms).

SourceDispatchService.php

Implements a priority-based dispatch algorithm across 24 hours:

  1. Solar first — free generation, use as much as available
  2. Utility grid second — grid electricity at standard tariff
  3. Generator last — diesel/backup only when solar + grid are insufficient

Returns hourly arrays for each source plus unmet demand and summary statistics used in the PowerBanner component.

SocketDemandService.php

Applies diversified demand factors to electrical outlet groups (based on IEC/NEC diversity):

  • Outlets 1–10: 100% demand factor
  • Outlets 11–20: 75% demand factor
  • Outlets 21+: 40% demand factor

Each outlet has a default of 200 VA. The service also applies a building-wide coincidence factor when pooling across floors.

SolarIrradianceService.php

Estimates hourly solar generation without external API calls:

  1. Computes solar declination using Spencer's equation (day of year)
  2. Derives sunrise/sunset from hour-angle formula
  3. Looks up Peak Sun Hours (PSH) from a built-in table (latitude × month)
  4. Distributes PSH as a sinusoidal curve between sunrise and sunset
  5. Applies a performance ratio of 0.80 (inverter losses, temperature, soiling)

Returns a 24-element array of watts per hour. Accuracy is ±10–15% vs measured data.

9. Authentication Flow

  1. User visits the app and clicks "Sign in with Google".
  2. Browser is redirected to /auth/google → Laravel redirects to Google's consent screen.
  3. User approves → Google redirects to /auth/google/callback.
  4. Laravel's GoogleController calls Socialite::driver('google')->user() to get the Google profile.
  5. User::updateOrCreate(['email' => ...]) — creates the user on first login, or updates their name/avatar on subsequent logins.
  6. A Sanctum bearer token is generated: $user->createToken('google-auth')->plainTextToken.
  7. The user is redirected to http://localhost:5173/auth/callback?token=XXX.
  8. The AuthCallbackPage reads the token from the URL, stores it in localStorage, and calls /api/user to load the profile.
  9. All subsequent API calls include Authorization: Bearer XXX via the Axios interceptor.
Important: There is no email/password registration. The only way for a user to get an account is to sign in with Google at least once. This means you can only add project members who have already logged in to the platform.

Restore Behaviour

  • If an entity with the same name already exists, the API returns a 409 Conflict with a message asking to overwrite.
  • If the user confirms, the existing entity is deleted and re-created from the backup.
  • All child entities (floors, rooms, components) are restored recursively.

Duplicate Feature

Duplicate creates a copy of any entity (building, floor, or room) within the same project, appending "(Copy)" to the name. Since the project-wide suggestion feature was added, a floor from any building can be duplicated into any other building in the same project.

12. Suggestion Dropdown (Copy From Existing)

When creating a new building, floor, or room, the name field shows a suggestion dropdown populated with existing entities from the entire project (not just the current parent).

Each suggestion has two buttons:

  • Empty — Pre-fills the name and area fields only. Creates a new empty entity.
  • Copy all — Duplicates the selected entity in full (all components, sub-rooms, etc.) into the current parent. Uses the duplicate API endpoint.

Project-wide endpoints used: GET /api/projects/{id}/all-floors and GET /api/projects/{id}/all-rooms.

13. Power Calculation Logic

Apparent Power (VA)

For each component: VA = power × power_factor × quantity

The TotalPowerController sums this across all four component tables (project, building, floor, room levels) plus socket demand. Two totals are returned:

  • max_va — all components regardless of schedule (peak design load)
  • total_va — components filtered to the current operating schedule (optimised load)

Socket Demand

Outlets are aggregated using diversity factors:

  • 1–10 outlets: 100% (e.g., 10 × 200 VA = 2,000 VA)
  • 11–20 outlets: 75% additional
  • 21+ outlets: 40% additional

Solar Generation

Computed from panel capacity (kW), project location (lat/lng), and month of year. Uses a lookup table of Peak Sun Hours (PSH) per latitude band and distributes output sinusoidally between sunrise and sunset.

Power Dispatch Priority

  1. Consume solar first (zero marginal cost)
  2. Draw remaining load from utility grid (if solar insufficient)
  3. Start generator only when both solar and grid are insufficient

14. Frontend Navigation Architecture

The app uses a context-based navigation pattern rather than deep URL parameters for most pages. A lightweight module navContext.js stores the current projectId, buildingId, floorId, roomId in memory. Pages read these with getNav() and write with setNav().

React Router handles top-level routes (/dashboard, /project, /project/building, /project/building/floor, etc.). The older URL-param style (used in RoomPage) coexists but is being phased out.

Because nav state is in-memory, refreshing a page at /project/building/floor loses the building context. This is a known limitation of the current architecture. A future improvement would be to persist IDs in URL params or sessionStorage.

SSL Note (Windows Localhost)

Guzzle (used by Laravel Socialite) fails SSL verification on Windows localhost. AppServiceProvider.php disables SSL verification in the local environment only: 

if (app()->environment('local')) {
    Socialite::extend('google', function ($app) {
        $config = $app['config']['services.google'];
        return Socialite::buildProvider(GoogleProvider::class, $config)
            ->setHttpClient(new \GuzzleHttp\Client(['verify' => false]));
    });
}

Deploying for Other Users

Currently the app runs only on localhost. For other users to access it, the backend must be deployed to a public server (Railway, Render, DigitalOcean, etc.) and the Google OAuth callback URL must be updated in both the Google Cloud Console and .env. The SQLite database should be replaced with MySQL or PostgreSQL for production use.
